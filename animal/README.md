# Myanmar Wildlife Encyclopedia

A Flask/SQLite encyclopedia backed by the real public records and photographs
from the [Myanmar Biodiversity Portal](https://www.myanmarbiodiversity.org/species),
plus a Myanmar-language chat experience powered by DeepSeek.

## Accounts

Only the landing page and the login/register screens are public. Browsing species,
categories, search and every chat requires an account: visit `/register`, then sign
in. Members-only pages redirect anonymous visitors to `/login?next=…` and return
them to the page they asked for once they sign in; the JSON endpoints answer `401`
instead of redirecting. `next` is restricted to same-site relative paths.

## Chat is per species, not site-wide

There is no global chat. Every species has its own chat at
`/animal/<id>/chat`, and it answers only about the one record the member is
looking at. Ecosystems and protected areas are reference pages: they have no
chat of their own, and no route serves one.

### Local records are retrieved first

A question is first matched against the current record, which is split into
labelled passages (habitat, threats, population, …). Only the passages that
actually speak to the question are put in the prompt, so an answer cannot
quietly draw on a part of the record the question was never about.

If nothing in the record answers the question, the chat retrieves relevant
public-source text and asks DeepSeek to answer from that text — see below.

Asking a species chat for a recipe, a bitcoin price or yesterday's football
score is a different matter: the model is **never called**, and the chat replies
with a short “not available” notice.

### When this project has not published the answer

If the question is about the current species — it names it, carries one of the
record intents, or uses animal vocabulary — but retrieval finds no relevant
passage, the server retrieves the species' Burmese and English Wikipedia
articles, its GBIF profile, and question-specific pages discovered from a
curated set of established wildlife, conservation, government, zoo and
research publishers (for example IUCN, WWF, Smithsonian, Animal Diversity Web,
BirdLife, CITES and scholarly publishers). It selects the relevant passages and
asks DeepSeek to answer in Burmese using only those passages. The exact external
pages used are shown under the answer. Population answers preserve the source's
estimate, range, date and geographic scope instead of turning unlike figures
into one number.

Search results are not fetched indiscriminately: only HTTPS pages on the
publisher allowlist can become evidence, scripts/navigation are removed, and
page text is explicitly treated as untrusted data rather than instructions.
The source panel is built by the server from the pages actually included in the
prompt, never from links generated by the model.

If no usable public article exists, or the retrieved pages still do not contain
the answer, DeepSeek's general knowledge and clearly identified inference become
the final fallback. The answer is saved with no source links. The model may make
a qualified best-effort inference, but it may not invent a precise changing
population figure, website, paper, URL, or citation.

The same public-source-first fallback happens when retrieval selected passages
but the grounded model response says that they do not answer the question. The
short refusal is held before display and replaced by the sourced response, so
the member does not see one response corrected by another.

An outside-source response stores its exact links with the message. A last-resort
general-knowledge response carries no record source panel and its explicit empty
source list is saved with the message. Off-topic questions remain a hard
boundary: recipes, prices, programming requests, and questions about another
record are handled locally and never sent to DeepSeek.

### Asking to see a photograph

“ဓာတ်ပုံ ပြပါ”, “အမ ဓာတ်ပုံ”, “show me the male photo” and the like are
answered from the record's own published files. The model is never asked for a
URL and never sees one, so it cannot invent a path or offer one picture as
another; the server resolves the file and attaches it to the reply as data, and
only paths under `/static/` are ever shown.

Species carry a cover photograph plus optional male and female photographs
uploaded through the Content Studio. Ecosystems and protected areas show every
photograph their record holds.

**A named sex is never answered with a stand-in.** If a member asks for the
female photograph and the record has only an unlabelled cover picture, the chat
says the photograph has not been added yet rather than passing the cover off as
the female — the same promise the importer makes about never substituting a
generic animal image.

### A question about another record gets one button

A question that names a *different* record never reaches the model either.
Nothing is generated: the member gets a one-line notice and a **single button**
to that record. Naming an ecosystem or a protected area is caught the same way
— that is what keeps a species chat from being asked about them at all — and
because those records have no chat, the button opens the record page instead.

Name matching is Myanmar-aware. It resolves a record by its full name, by its
head noun (“ဆင်” finds “အာရှဆင်”, “elephant” finds Asian Elephant), or by a
phonetic spelling variant, and it prefers the longest match so “ကျားသစ်”
resolves to the Clouded Leopard rather than to “ကျား”. A head noun that fits
many records at once identifies none of them — “လိပ်” ends a dozen turtle names
— so it never picks one arbitrarily.

Matching is deliberately literal rather than phonetic, because Burmese phonetic
keys collapse real distinctions: “သည်”, the ordinary copula, keys identically to
“ဆင်”, and a phonetic rule would send almost every sentence to the elephant.

The suggested openers on each page are generated from the fields that record
actually has, so the member is never offered a question the record cannot
answer.

Completed user/assistant exchanges are saved in SQLite for the signed-in member
and restored when that species chat is opened again. The server supplies trusted
saved history to the generator; chat history submitted by a browser client is
ignored.

### The chat workspace

The chat page is a full-height application rather than an article: the page
itself does not scroll, the message list and the history rail scroll on their
own, and the composer stays on screen while a long answer streams in.

The rail on the left lists the member's recent species conversations, newest
first, with a plain-text preview of the last reply — Markdown is stripped, so a
table does not show up as a row of pipes. Each row carries its own **delete**
button, and the header carries **မှတ်တမ်း ဖျက်ရန်** for the conversation on
screen; both confirm first and both are scoped to that one member and that one
species. Below 980px the rail becomes a drawer opened from the header.

### Seeing the pipeline run

### The Content Studio searches the way members do

The library search in `/admin` is the member search — `fuzzy_search_animals` for
species, `filter_records` for ecosystems and protected areas, over the same
fields. It used to be a casefolded substring over three columns, which missed
everything Myanmar text needs: it could not see an alias, so **ကျားတိမ်** found no
clouded leopard; it could not normalise, so a name carrying an invisible U+200C
matched nothing; and it never looked at a record's own text, so **ဖျံ** found five
otters instead of eleven records. An administrator now gets every match rather
than the member suggestion cap of fifty, and the collection field lists live in
`portal_collections.SEARCH_FIELDS` so the two sides cannot drift apart.

**Content Studio → Retrieval pipeline** (`/admin/rag`) runs any question against
any record and shows all twelve steps with their real intermediate values:
normalisation, Myanmar syllable segmentation, stopword removal, the strong and
weak matching units, the scope gate, the photo gate, the passage index, the
detected intents, a per-passage score table against the active threshold, and
the exact system prompt the model would receive. Everything on that page is
produced by the same functions the chats call — `rag.trace()` calls
`find_subject`, `question_intents`, `_overlap_score` and `retrieve` directly —
so the console cannot drift into describing a pipeline the site no longer runs.

The console's comparison table maps each classic RAG stage onto what this site
does instead.

It ends with the **final response** — the reply a member would actually get.
Three of the four branches (hand-over, photographs, refusal) are written by the
site itself, so the console renders their exact wording with no model involved,
pulled from the same functions the chat endpoints call rather than a second
copy that could drift. The fourth calls the model, so it is offered as a button
instead of running on page load, and it streams the answer back with the
generator, first-token time, total time and the passages it was given.

That bench run **reads no history and saves none** — it is repeatable, and an
administrator's own conversation never colours what the next question
retrieves. Its generator is a dropdown of the models the DeepSeek key can call, so
the same retrieved passages can be put to two models and compared. That is the
way to settle whether a weak answer is a retrieval problem or a generator
problem: if both models answer thinly from the same passages, the fault is in
what was retrieved, or in the record.

### OpenAI embeddings, local vectors, and offline member chat

Retrieval is primarily **lexical**: adjacent Myanmar syllables are joined into
pairs, whole Latin words are kept, and a passage scores by how much of that set
it shares with the question, plus a bonus when the question's intent matches the
passage's tags.

OpenAI's `text-embedding-3-small` model and a local SQLite vector store sit
beside lexical retrieval. Embeddings can only **add** passages to a selection;
they never displace or reorder a lexical hit. The API key stays in the admin
Flask process and is never sent to member browsers.

* Cosine similarity has no zero. An unrelated question still returns its best
  passage, so a bar set "in the middle" would quietly answer questions the
  record cannot answer. The honest refusal is a lexical guarantee.
* Thresholds must be evaluated on this Myanmar corpus. Judge them in the admin
  console by typing a question and reading the `cosine` column. Set
  `EMBED_ENABLED=0` to run lexical retrieval only.

Identity passages never win a semantic slot: they are short strings that rank
near the top for any question at all, and they are appended to every selection
anyway.

**Member chat never calls OpenAI and never writes a vector.** Administrators
build the complete index for animals, ecosystems, and protected areas from
Content Studio → Retrieval Pipeline → **Full OpenAI index**, or from the CLI:

```bash
flask --app app embed-warm
```

Publishing a new or edited record also indexes that record immediately while
the administrator is online. Vectors are keyed by `(model, sha256(passage
text))`, while `embedding_passages` maps every vector to its content type,
stable record key, label, and position. The full command is resumable, removes
stale mappings after success, and reports completeness for all three catalogs.

Semantic query comparison requires a query vector from the same model. The
admin RAG console may create and cache that vector online. A member asking that
exact question later can use the cached vector entirely offline; every other
member question falls back to the Myanmar-aware lexical pipeline. This is the
only way to keep member requests offline while using a hosted OpenAI embedding
model—arbitrary unseen questions cannot receive a new OpenAI vector offline.

| variable | default | meaning |
| --- | --- | --- |
| `OPENAI_API_KEY` | empty | admin-only key required to create vectors |
| `OPENAI_BASE_URL` | `https://api.openai.com/v1` | OpenAI-compatible API base |
| `OPENAI_EMBED_MODEL` | `text-embedding-3-small` | embedding model used for passages and admin questions |
| `OPENAI_EMBED_DIMENSIONS` | `1536` | stored vector dimensions |
| `EMBED_ENABLED` | `1` | `0` turns semantic recall off entirely |
| `EMBED_THRESHOLD` | `0.55` | cosine a passage must clear to be added |
| `OPENAI_EMBED_TIMEOUT` | `60` | admin request read timeout; member chat never waits on it |
| `OPENAI_EMBED_BATCH_SIZE` | `64` | passage inputs per admin API request |

## Data import

The importer reads the portal catalog, fetches each structured bilingual species
record, verifies non-empty WebP photographs from the public image repository used
by the portal, downloads them locally, and atomically replaces the generated seed
database. The cached crawl holds 81 assessed records — 30 Mammals, 21 Birds and
30 Reptiles — each with a verified photograph. The legally protected mammals that
the portal does not publish are added separately, by the importer described
below. A record the portal supplies without
a class is labelled “Unclassified” rather than guessed at; none of the current
records need that fallback. The site never hard-codes these totals: every count it
displays is read back out of SQLite at request time.

```bash
cd /Users/myominko/Developer/animal/myanmar_wildlife
source venv/bin/activate
pip install -r requirements.txt
python crawler.py
```

The crawl is cached in `myanmar_wildlife/data/myanmar_biodiversity_species.json`.
To rebuild SQLite later without network access:

```bash
python crawler.py --from-cache
```

Before replacement, the importer makes a timestamped `wildlife.db.bak-*` backup.
Species without a verified source photo are displayed with an honest “photo not
available” panel; a generic animal image is never substituted. `--from-cache`
refuses to run if the cache file's own `count` disagrees with the records it
holds, so a truncated cache cannot quietly seed a short database.

### The Protected Wildlife List (2020)

`crawler.py` can only publish what the portal holds, and fewer than a third of
Myanmar's legally protected mammals appear there — no pangolin, no otter, no
linsang, and none of the twenty-four whales, dolphins and porpoises. A second
importer publishes the full schedule of **77 totally protected mammals**:

```bash
cd /Users/myominko/Developer/animal/myanmar_wildlife
source venv/bin/activate
python protected_mammals.py
```

The list itself — Myanmar name, English name and scientific name for all 77 —
is kept as data in `data/totally_protected_mammals_2020.json`, and everything
else is assembled from four public sources, each recorded on the record it
supplied: **Wikidata** for the global IUCN category, **Wikipedia** for the prose,
**GBIF** for order and family, and **Wikimedia Commons** for the photograph and
the photographer and licence the licence requires us to print.

Unlike `crawler.py`, this importer is **additive and idempotent**. It never
deletes a row. Twenty-one of the 77 were already published from the portal:
those keep the portal's own Burmese text and photograph and are only marked as
protected, with the list's names added as searchable aliases. The other 56 are
created. Re-running refreshes only the rows this importer owns — the portal's
records are never overwritten — and `--refresh-images` re-fetches photographs
already on disk.

**A lead image is not automatically a photograph of the animal.** The pygmy
sperm whale's Wikipedia article leads with a size-comparison silhouette, the
leaf muntjac's with a distribution map, and Commons files a museum photograph
of *Muntiacus feae* under the category for *Muntiacus gongshanensis*. Every
candidate is therefore checked against its Commons categories and rejected if it
is a map, a size chart, a skeletal mount or a specimen; a file found by search
rather than placed by Wikipedia's own editors must additionally name this
species and no other from its genus. Where nothing survives that test the record
is published with no photograph at all — three of the 77 are — because the “photo
not available” panel is the honest answer and a stand-in is not.

Prose is taken in Burmese where Burmese Wikipedia has an article (35 of the 77)
and in English otherwise, the same per-field fallback `crawler.py` already uses
for the portal's own `_mm` fields. A record shown in English says so under its
sources.

### Notification 690/2020 — the protected birds

The bird schedule is shaped differently, and the difference matters. Nineteen of
its forty-eight entries name a species; the other twenty-nine protect a whole
**family, order or genus** — every owl, every stork, every pitta.

```bash
python protected_birds.py
```

So a record is not always a species. `animals.taxon_rank` says what it is, and a
group record has no IUCN category, because a family does not have one. It shows a
photograph only when the file itself names which member species it depicts, that
name is confirmed against GBIF to be a real species inside the group, and the
caption says so — **ဤအုပ်စုမှ ဥပမာ — *Mycteria ibis***. A picture captioned as the
family would be passing one bird off as a hundred others. The lead image
Wikipedia's own editors chose wins whenever it names a member; only when it names
none are the article's other pictures considered, which is what keeps a fossil
genus mentioned in some category list out of the caption. One entry — the genus
*Aquila* — ends up with no photograph, and says so.

A group record also lists the species already in this encyclopedia that it
covers, each with the level it inherits, and links to them.

**Protecting a family protects the birds already published here.** After writing
the schedule the importer walks every bird in the catalog and applies the level of
the *most specific* entry that covers it — species beats genus beats family beats
order, and where two are equally specific the stricter level wins. Eight existing
records were protected this way without being named anywhere in the notification,
and `protection_basis_my` records which entry did it, so the claim on the page is
traceable:

| Record | Level | Because |
| --- | --- | --- |
| Slender-billed Vulture | Totally protected | Accipitridae |
| Greater Adjutant, Black-necked Stork, Storm's Stork | Totally protected | Ciconiidae |
| River Tern, Black-bellied Tern | Totally protected | Laridae |
| Gurney's Pitta | Totally protected | Pittidae |
| White-bellied Heron | Normally protected | Ardeidae |

The precedence rule is what keeps the Green Peafowl totally protected by its own
entry rather than demoted to Phasianidae's normal protection.

### Myanmar name variants, and the group words

One animal carries several Myanmar names. The clouded leopard is အင်းကျား,
သစ်တောကျား and ကျားတိမ်; the sun bear is ခွေးဝံ and ဝက်ဝံငယ်; the fishing cat is
ငါးဖမ်းကြောင် and ငါးစားကြောင်. A reader should find the record by whichever name
they know.

```bash
python name_variants.py
```

`data/myanmar_name_variants.json` holds 51 entries and 100 Myanmar names. Every
variant is stored as a searchable alias, and **an existing record is never
renamed** — the Myanmar name it already publishes stays, and the variants join
it. Twenty-four records gained 43 new aliases this way.

Twenty-four entries named a taxon the catalog did not hold. A few are species —
the sambar, the wild boar, the Popa langur, the Indian rhinoceros. Most are the
everyday **group words**: ဖျံ is otters, ရှဉ့် is squirrels, ကြံ့ is rhinoceroses,
မျောက် is macaques. Those are published as taxon-group records, exactly as
Notification 690/2020's family entries are, and each one lists the species
already in the encyclopedia that it covers — ဖျံ links to all four otters, ကြံ့ to
three rhinoceroses, သင်းခွေချပ် to both pangolins.

**A group's example photograph must show an animal found in Myanmar.** Ranking
candidates on identity alone gave the fox genus an Arctic fox and the rhinoceros
family two African white rhinos — truthfully captioned, and the wrong picture for
this encyclopedia. Examples are now preferred when the species appears in this
catalog or in the official 2020 schedules, so ဖျံ shows *Lutra lutra*, ကြံ့ shows
*Rhinoceros unicornis*, and မြေခွေး shows *Vulpes vulpes*. The same rule improved
the bird groups: စွန်မျိုးများ now shows a shikra rather than a European buzzard.

### Place names are looked up, not translated

The portal publishes a species' states and protected areas in English only.
Neither needs translating: `myanmar_places.py` maps the fifteen states and
regions to their official Myanmar names, and resolves protected areas against the
portal's own cached catalog, which already carries a Myanmar name for 55 of its
73 areas. 39 of the 45 areas the species records mention resolve exactly; the six
that do not are areas the portal itself publishes no Myanmar name for, and they
stay in English rather than being guessed at.

Every one of the 77 mammals and 48 bird entries carries its legal status in
`protection_status_my`,
`protection_status_en` and `protection_law_my`. The species page opens with a
notice naming the law and the list entry, the catalog cards carry a
**ဥပဒေအရ ကာကွယ်** badge, the Content Studio can edit them, and the status is an
*identity* passage in retrieval — so a chat about a protected species carries its
legal status into every answer, not only into answers about the law.

The two schedules are the same instrument, so both cite it the same way:
Conservation of Biodiversity and Protected Areas Law (2018), Notification No.
690/2020.

## IUCN categories carry their meaning

A member reading "EN" on a badge learns nothing, so every assessment on the
site is rendered from one category table in `iucn.py`: the code stays the
headline, the Burmese name sits beside it where there is room, and the English
long form plus a one-line Burmese description are always in the tooltip. The
species and ecosystem catalogs each carry a collapsible legend listing every
category on the scale they use.

The two scales are kept deliberately apart. Species are assessed on the **Red
List of Threatened Species**, whose end point is extinction (မျိုးသုဉ်း);
ecosystems are assessed on the **Red List of Ecosystems**, whose end point is
collapse (ပြိုကွဲပျက်သုဉ်း) and which has **CO — Collapsed** where the species
scale has EX and EW. They share their letter codes, which is exactly why the
wording must not be shared: rendering an ecosystem's CR with the species
wording would tell a member a swamp forest is about to go extinct.

Ecosystem assessments are written as an outcome plus a plausible range —
`CR (CR-CO)` is an overall CR whose uncertainty spans CR to CO. The badge
prints the whole string and colours it by the leading code.

`CR`, `EN` and `VU` are the *threatened* categories (`iucn.is_threatened`);
`NT` sits next to them and is not one of them. `DD` does not mean safe, and
`NE` means no assessment was ever attempted.

The same table feeds two non-visual places: `species_sources.IUCN_CODES`, which
normalises written-out assessments while crawling, and the conservation-status
passage the chat retrieves — which is stored expanded ("EN — Endangered
(မျိုးသုဉ်းရန် အန္တရာယ်ရှိ)။ …") so a member asking what the status *means* is
answered from the record rather than from the model's own knowledge.

## Connect the DeepSeek generator

Member chat is generated by [DeepSeek](https://platform.deepseek.com/)'s
OpenAI-compatible chat completions API. The key is read from `.env` and is
**server-side only**: it is never rendered into a page and never reaches
browser JavaScript.

1. Put the key and model in `myanmar_wildlife/.env`:

   ```
   DEEPSEEK_API_KEY=your-key
   DEEPSEEK_BASE_URL=https://api.deepseek.com
   DEEPSEEK_MODEL=deepseek-flash
   DEEPSEEK_TEMPERATURE=0.2
   DEEPSEEK_MAX_TOKENS=1600
   ```

   `config.py` loads `.env` itself, so the key works under both `flask run`
   and `python app.py`.

2. Start the website:

   ```bash
   cd /Users/myominko/Developer/animal/myanmar_wildlife
   source venv/bin/activate
   flask --app app run --debug --host 127.0.0.1 --port 2000
   ```

3. Sign in, open any species, and press **ပြောဆိုခန်း ဖွင့်ရန်** — for example
   [http://127.0.0.1:2000/animal/2/chat](http://127.0.0.1:2000/animal/2/chat),
   then ask it something.

No page displays the connection, but `GET /api/llm-status` still reports it as
JSON — model name and reachability only, never the key. To use a different
model, change `DEEPSEEK_MODEL` to an id the key can serve. Without a key, or with
one that cannot call the configured model, the chat answers 503 with a clear
message rather than opening an empty stream.

### Answers are Markdown

Every prompt asks for GitHub-flavoured Markdown and, for anything comparing two
or more facts, a real Markdown table (header row, `| --- |` delimiter, one row
per line). `static/js/markdown.js` renders it in the chat bubble: tables,
headings, lists, blockquotes, code and links. The text is HTML-escaped before
any markup is built, so a reply cannot inject elements or attributes, and link
targets are limited to `http(s)` and site-relative URLs.
